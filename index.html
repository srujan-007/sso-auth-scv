💡 The one-sentence version

When a rep opens a console page that has Omni-Channel, Salesforce silently signs them in to Amazon Connect (the phone system). If that silent sign-in works, the dial-pad lights up. If anything in the chain is wrong, the dial-pad just stays grayed out — usually with no error message. Your job is to find which link in the chain broke.

🎟️ An analogy that makes everything else easier: the conference badge

Imagine you work for Salesforce and you’re visiting a conference venue run by Amazon Connect. You don’t have a separate venue account. Instead your employer writes a signed letter of introduction, and venue security checks it. Almost every SSO error in this guide maps onto something that can go wrong with that letter:

In the analogyIn real lifeIf it goes wrong…

#3 Response signature invalid — the stamp doesn’t match the one security has on file (or it expired)

The venue’s guest listContact Center Users#5 Access denied – not onboarded — the letter is fine, but you’re not on the list
The wristband you get once insideCCP session cookieWithout it, nothing downstream works

🤫 Why does it fail silently?

All of this runs in a hidden frame before the connector has even started. So when it breaks, there’s often no error event and no pop-up — just a grayed-out dial-pad. That’s why we have a trick (the manual SSO test) that drags the invisible process into a normal browser tab where you can read the error.

🔀 Two families of problems

Access problems (#1, #5): is this person allowed? → permissions & membership.
Trust-setup problems (#2, #3, #4): do Salesforce and AWS still agree on stamp & name? → certificate, Issuer, metadata.
Knowing which family you’re in halves your search.

    5Hands-on lab: run the manual SSO test

    This is the single most useful trick in this guide. It makes the invisible sign-in happen in a normal tab, so Salesforce or AWS shows you the actual error.

    🗣 Facilitator cueDo this live on a sandbox. Have one volunteer play “the rep”. Deliberately break something beforehand (e.g. remove the rep from Contact Center Users) so the room sees a real error screen.

    Part A · The admin gets the link Admin

    Part B · The rep opens it Affected rep

    Why the affected rep?

    The test runs as whoever opens it, so it reproduces that person’s access and permissions. Running it as an admin could hide the problem.

    Part C · What do you see? (click one)

    👆 Pick the screen the rep sees to get the diagnosis and the fix.

    ⚠️ Golden rule — memorise this one

    After any change to the certificate or Issuer in Salesforce, you must re-export the SAML metadata from the Salesforce Identity Provider page and click Replace Metadata on SalesforceServiceVoiceIdp in AWS Management Console → IAM → Identity providers. Forgetting this is the #1 reason “I fixed it but it’s still broken”.

    ✅ After a fix, always reset cleanly before re-testing

    1. Open the test link; on the Amazon Connect home page click your username (top-right) → log out.
    2. Open the console app that has Omni-Channel, then open DevTools (F12).
    3. Right-click the browser’s refresh button → Empty Cache and Hard Reload.
    4. Once the page fully loads, set Omni-Channel to Available (or Busy) for Voice and check the dial-pad.

    A stale session can make a working fix look like it failed.

    6Your 7-step triage routine

    When a ticket says “dial-pad is grayed out”, work through these in order. Each step either finds the problem or rules out a whole stage.

    1. Scope the symptom.Is the dial-pad grayed while the rep is Available? One user or many? New setup, or did it stop working? Any recent certificate or Connected App change? Many users + recent change → think certificate/Issuer. One user → think access.
    2. Verify Voice permissions.Setup → Users → the rep → Permission Set License Assignments: “Salesforce Voice with Amazon User” (Amazon Connect) or “Salesforce Voice User (Partner Telephony)”. Then Permission Set Assignments: “Salesforce Voice Permission Set” or equivalent.Catches error #1
    3. Verify Contact Center membership.Setup → Contact Centers → your CC → Contact Center Users. Rep listed, with the Admin or Agent permission set? If already listed but failing, remove, save, re-add, save to re-sync with Amazon Connect.Catches error #5
    4. Run the manual SSO test.Use the lab above. Read the outcome.
    5. Apply the error-specific fix.Errors #2, #3 and #4 all finish with “re-replace the metadata in AWS”.
    6. SSO is fine but still grayed?DevTools → Network → filter ccp-v2. If you see net::ERR_NAME_NOT_RESOLVED, the instance name in the Contact Center metadata is wrong.
    7. Clear cache and re-test.Log out of Amazon Connect → Empty Cache and Hard Reload → set Available → confirm the dial-pad is active.

    🛠 Diagnostic toolbox

    Manual SSO test — Setup → Contact Centers → your CC → right-click Telephony Provider Settings → Copy Link Address → rep opens it in a new tab.
    Is the CCP reachable? — F12 → Network → filter ccp-v2. ERR_NAME_NOT_RESOLVED = bad instance name; 200s = reachable. Save a HAR for escalations.
    Streams log — in the DevTools Console: 
    connect.getLog().download();  // attach to escalations
connect.version();            // confirm the Streams version
    Connection Status utility (Amazon Connect only) — runs the endpoint test and browser-requirements check from the rep’s desktop.
    Page won’t load at all? Look in the Console for ERR_BLOCKED_BY_CLIENT (browser extension), X-Frame-Options/CSP (framing blocked), CORS (allowlist the domain), or a Storage-Access SecurityError (third-party cookies).

    🪤 “It worked yesterday” traps

    SettingWhat goes wrong → fix
    Require first-party use of Salesforce cookies (My Domain)SSO fails / cookie issues → turn off, reload
    Include Permissions-Policy HTTP header (Session Settings)Mic/speaker blocked → keep off, or always allow mic & speaker
    Third-party cookies blocked in the browserSSO loop / Storage-Access errors → allow them for Salesforce + Amazon
    Force re-login after “Log in as”Calls can drop ~15–20 min after an admin uses “Log in as” → see the Session-Settings doc
    High Assurance on the Connected AppHA-gated OAuth can block SSO → relax HA or satisfy the assurance level

    ✅ You’re done when…

    • The manual test lands on the Amazon Connect home page
    • ccp-v2 requests return 200
    • No AUTH_* or ACCESS_DENIED events
    • Rep is in Contact Center Users
    • Cert valid, Issuer blank, AWS metadata re-replaced
    • After a clean reset, Available → dial-pad enabled

    📣 Escalate to engineering only when…

    All prerequisites are verified, the manual SSO test succeeds, the CCP is reachable — and the connector still fails to initialise, or the platform keeps returning 500s.

    Attach: Org ID + User ID + timestamp, the exact error-screen text, HAR + Streams log + console output, and which triage steps you already did.
